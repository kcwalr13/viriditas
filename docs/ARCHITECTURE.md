# Viriditas — Architecture Overview

**Purpose:** how the system fits together — auth/session model, rendering and data-fetching
patterns, the two-layer plant profile design, and the AI pipeline. Read this before making
structural changes. Conventions and gotchas for day-to-day coding live in
[CLAUDE.md](../CLAUDE.md).

## System shape

```
┌────────────────────────────┐         ┌─────────────────────────────────┐
│  Browser (desktop/mobile,  │  HTTPS  │  Vercel — Next.js 15 App Router │
│  installable as a PWA)     │◄───────►│  Server Components + middleware │
└─────────────┬──────────────┘         └─────────────────────────────────┘
              │ supabase-js (anon key + user JWT)
              ▼
┌─────────────────────────────────────────────────────────────┐
│  Supabase                                                   │
│  • Auth (email/password; cookie sessions via @supabase/ssr) │
│  • Postgres + RLS (per-user rows; shared species cache)     │
│  • Storage: public `plant-photos` bucket                    │
│  • Edge Functions (Deno): analyze-plant, diagnose-plant,    │
│    fetch-species-info, identify-species, suggest-species    │
└───────────────────────────┬─────────────────────────────────┘
                            │ server-side fetch (keys never in browser)
                            ▼
              Anthropic Claude API (sole provider since v1.8.0:
              claude-haiku-4-5; claude-sonnet-4-6 for diagnose-plant)
```

There is no Next.js API layer of our own: the browser talks to Supabase directly (RLS is the
authorization boundary for data), and anything involving AI keys runs in Edge Functions.

## Auth & session model

- `@supabase/ssr` everywhere: `lib/supabase/client.ts` (browser, `createBrowserClient`) and
  `lib/supabase/server.ts` (Server Components, `createServerClient` reading cookies).
- **`middleware.ts` runs on every request** (minus static assets): refreshes the session
  cookie and gates routes. It validates with `getUser()` (server-verified), *not*
  `getSession()` (just reads the local cookie).
- Public (no-session) routes are exactly `/sign-in`, `/sign-up`, `/forgot-password`, `/auth`.
  Everything else redirects signed-out users to `/sign-in`. Only `/sign-in` and `/sign-up`
  bounce signed-in users to home — `/auth` must stay reachable mid password-reset.
- `app/(app)/layout.tsx` re-checks `getUser()` server-side as a second line of defense.
- **Password reset:** `/forgot-password` calls `resetPasswordForEmail`; the email link lands
  on `/auth`, which exchanges the one-time PKCE code for a session and lets the user set a
  new password.
- Sign-out: `supabase.auth.signOut()` then `router.push('/sign-in')` + `router.refresh()`.

## Rendering & data-fetching patterns

Two deliberate patterns, chosen per screen:

1. **Server Components for list screens** (Today `app/(app)/page.tsx`, Plants
   `app/(app)/plants/page.tsx`): fetch plants, then photos + care logs via
   `.in('plant_id', ids)` in a `Promise.all` — 3 queries regardless of collection size —
   and enrich into card models in JS. After any client-side mutation, call
   `router.refresh()` so the server recomputes.
2. **One big Client Component for Plant Detail** (`app/(app)/plant/[id]/page.tsx`): the
   screen is interaction-dense (uploads, care dock, edit mode, AI analysis, lightbox), so
   all data loads client-side; the log book paginates with server-side `.range()`.

**Hydration rule (learned the hard way in v1.5.0/v1.5.1):** never read the clock
(`new Date()`, `Date.now()`) or `localStorage` in the render body of a client component that
gets server-rendered. Vercel renders in UTC; the browser renders in local time; React throws
error #418. Compute time-derived values in a mount effect (`now: Date | null` state) and
render deterministic fallbacks until set.

## The two-layer plant profile

Every plant's profile combines:

- **Layer 1 — personal data** (per-user, evolving): the `plants` row, `photos`, `care_logs`
  (including categorized notes and structured measurements), `analysis_results`,
  `diagnoses`, `propagations`. Protected by per-user RLS.
- **Layer 2 — species reference** (global, cached): one `species_profiles` row per species,
  generated by AI **at most once per species ever**, then shared by all users. Refreshable
  on demand (`forceRefresh`).

The species name that links the layers can come from two places — `plants.species` (manually
entered) or the latest `analysis_results.species` (AI-identified). Always resolve as
`plant.species || latestAnalysis?.species`; using only one makes species UI look broken.

## The AI pipeline

| Flow | Path |
|---|---|
| Health analysis | Plant Detail gathers context (species profile, previous analyses w/ scores + prior advice, recent care logs w/ categories + measurements, plant context, season) → `analyze-plant` fetches the photo from Storage and calls the model → client saves the result to `analysis_results` |
| Species profile | `fetch-species-info` → cache hit returns instantly; miss generates + upserts with the service role |
| Photo ID | Explore / Add Plant send base64 → `identify-species` → name + confidence only |
| Name search | Explore → `suggest-species` → 4–6 candidates → browser adds Wikipedia thumbnails client-side |
| Diagnosis session (v1.7.0) | Diagnose screen → `diagnose-plant` assembles context **server-side** (plant row, species profile, logs, analyses, prior diagnoses) + transcript + session photos → one of question / photo_request / verdict; ≤3 ask-turns, then a forced verdict → `diagnoses` row + client-inserted `care_recommendations` proposals |

Full contracts: [EDGE-FUNCTIONS.md](EDGE-FUNCTIONS.md).

**Provider:** Claude only — the `AI_PROVIDER` switch and Gemini branches were retired
in v1.8.0 (spec decision #1). Haiku on the volume paths, Sonnet on `diagnose-plant`.

**Security model (since v1.5.0):** all five functions are deployed `--no-verify-jwt` but
authenticate every call via `getUser()`; `analyze-plant` only fetches images from this
project's `plant-photos` bucket (SSRF guard) and detects media type from magic bytes;
`diagnose-plant` only accepts session-photo paths under the caller's own
`{userId}/{plantId}/diagnosis/` prefix and writes sessions with the service role;
`fetch-species-info` whitelists AI output fields before writing the shared cache;
`identify-species` enforces a MIME allowlist.

**Cost control by design:** species profiles are generated once per species globally;
re-analysis sits behind a confirm dialog + cooldown; `suggest-species` skips the AI for
empty queries.

## Deployment notes

- Vercel auto-deploys `main`. Framework preset **Next.js**, output directory **default** —
  both were misconfigured Expo leftovers once; don't regress them.
- `npm run build` runs `scripts/patch-ua-parser.js` first: it strips a `__dirname` reference
  from the ncc-compiled `ua-parser-js` bundle that crashes Vercel's Edge Runtime (where the
  middleware executes). It must re-run after every fresh `npm install`.
- **After pushing, check the Vercel dashboard.** A lint error once failed every build for
  six weeks while production silently served the previous version (v1.4.0 → v1.5.0 lesson).
- `next.config.ts` allowlists `*.supabase.co/storage/v1/object/public/**` for `next/image`.
- The app is a PWA (`public/manifest.json`); web push is intentionally **not** implemented
  (`lib/notifications.ts` is a no-op stub).
